## The pipeline

Nine skills take a feature from an agreed problem to an audited pull request. `spec-workflow` is the map of the steps, and `setup` runs once per project. Every `sdd:` step writes a file into the work item, `project/work-items/{NN}-{name}/`, so the record of what was agreed, reviewed and verified stays in the repository. The three gates block the next step: the design and task reviews on a CRITICAL finding, and the implementation audit on a CRITICAL or MAJOR finding.

<Pipeline />

The [superpowers](https://github.com/obra/superpowers) plugin is an alternative for steps 8 and 12. A bugfix runs a shorter path with no gates: `spec-generator` writes `bugfix.md`, `design.md` and `tasks.md`, superpowers implements them, and `spec-finish` opens the pull request. The [spec-workflow page](/sdd-skills/skills/spec-workflow/) has both tables and the rules that override superpowers' default order.

## Who it's for

Teams that need to show why the code does what it does. Each work item keeps its requirements in EARS notation, the design, the review verdicts, the test plan and an implementation audit backed by pasted build and test output. A reviewer, an auditor or the next engineer can read the decision trail without asking the agent that wrote it.

Teams that want a gate to stop the agent, not only to advise it. The design review, the task review and the implementation audit each return a blocking status, and a second blocking run hands the decision back to a person.

It is a poor fit for a quick prototype. The pipeline asks for your approval at every phase, and that costs time you may not want to spend on throwaway code.

## How it compares

All four tools write a spec before code. The differences are in what can stop the work and what happens after the code is written. The table is as of November 2026, and each cell for another tool comes from the linked repository or docs page.

| | SDD Skills | [Spec Kit](https://github.com/github/spec-kit) | [Kiro](https://kiro.dev/docs/specs/) | [OpenSpec](https://github.com/Fission-AI/OpenSpec) |
|---|---|---|---|---|
| Form | Agent skills (`SKILL.md`) | CLI and agent commands | [IDE and CLI](https://kiro.dev/license/) | CLI and agent commands |
| Spec format | EARS requirements, design, tasks | Spec, plan, tasks, checklists | [EARS requirements](https://kiro.dev/docs/specs/correctness/), design, tasks | Proposal, design, tasks, spec deltas |
| Blocking review gates | Design review and task review block on CRITICAL | `plan` stops on failed constitution checks; `analyze` only reports | You [review and approve each phase](https://kiro.dev/docs/specs/); [Analyze Requirements](https://kiro.dev/docs/specs/analyze-requirements/) is an optional check; a [Pre Tool Use hook](https://kiro.dev/docs/hooks/types/) can block a tool call | Validation blocks malformed changes; verify does not block |
| Audit after coding | Implementation audit, FAILED on CRITICAL or MAJOR | `converge` adds the gaps as new tasks | [Optional property-based tests](https://kiro.dev/docs/specs/correctness/) from the EARS requirements, in the IDE | `verify` grades findings, does not block |
| Older specs | `spec-maintenance` annotates superseded specs | By team convention | [Sync Files](https://kiro.dev/docs/specs/quick-spec/) regenerates tasks after a requirements edit | Deltas merge into the live specs |
| Licence | MIT | [MIT](https://github.com/github/spec-kit/blob/main/LICENSE) | [Proprietary, under the AWS Customer Agreement](https://kiro.dev/license/) | [MIT](https://github.com/Fission-AI/OpenSpec/blob/main/LICENSE) |

Choose Spec Kit or OpenSpec if you want a CLI that works across many agents with less ceremony. Choose Kiro if you want specs built into the editor. Choose these skills if you want review verdicts and an audit kept as files, and gates that stop the agent. They need superpowers only to implement a bugfix, and they are tested mainly with Claude Code. The [Evals page](/sdd-skills/evals/) shows how each skill scores against a baseline run.
