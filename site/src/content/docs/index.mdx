## The pipeline

Seven skills take a feature from an agreed problem to an audited implementation. `spec-workflow` is the map of the steps, and `setup` runs once per project. Every `sdd:` step writes a file into the work item, `project/work-items/{NN}-{name}/`, so the record of what was agreed, reviewed and verified stays in the repository. The three gates block the next step: the design and task reviews on a CRITICAL finding, and the implementation audit on a CRITICAL or MAJOR finding.

<Pipeline />

Steps 8 and 12 hand off to the [superpowers](https://github.com/obra/superpowers) plugin. A bugfix runs a shorter path with no gates: `spec-generator` writes `bugfix.md`, `design.md` and `tasks.md`, and implementation follows. The [spec-workflow page](/sdd-skills/skills/spec-workflow/) has both tables and the rules that override superpowers' default order.

## Who it's for

Teams that need to show why the code does what it does. Each work item keeps its requirements in EARS notation, the design, the review verdicts, the test plan and an implementation audit backed by pasted build and test output. A reviewer, an auditor or the next engineer can read the decision trail without asking the agent that wrote it.

Teams that want a gate to stop the agent, not only to advise it. The design review, the task review and the implementation audit each return a blocking status, and a second blocking run hands the decision back to a person.

It is a poor fit for a quick prototype. The pipeline asks for your approval at every phase, and that costs time you may not want to spend on throwaway code.

## How it compares

All four tools write a spec before code. The differences are in what can stop the work and what happens after the code is written.

| | SDD Skills | [Spec Kit](https://github.com/github/spec-kit) | [Kiro](https://kiro.dev/docs/specs/) | [OpenSpec](https://github.com/Fission-AI/OpenSpec) |
|---|---|---|---|---|
| Form | Agent skills (`SKILL.md`) | CLI and agent commands | IDE, CLI and web app | CLI and agent commands |
| Spec format | EARS requirements, design, tasks | Spec, plan, tasks, checklists | EARS requirements, design, tasks | Proposal, design, tasks, spec deltas |
| Blocking review gates | Design review and task review block on CRITICAL | `plan` stops on failed constitution checks; `analyze` only reports | You approve each phase; no automated review gate confirmed | Validation blocks malformed changes; verify does not block |
| Audit after coding | Implementation audit, FAILED on CRITICAL or MAJOR | `converge` adds the gaps as new tasks | Optional property-based tests | `verify` grades findings, does not block |
| Older specs | `spec-maintenance` annotates superseded specs | By team convention | Sync Files updates `tasks.md` | Deltas merge into the live specs |
| Licence | MIT | MIT | Proprietary | MIT |

Choose Spec Kit or OpenSpec if you want a CLI that works across many agents with less ceremony. Choose Kiro if you want specs built into the editor. Choose these skills if you want review verdicts and an audit kept as files, and gates that stop the agent. They need superpowers for implementation today, and they are tested mainly with Claude Code.
