# Spec Task Review — Quality Gate

Validate that `tasks.md` is complete, correctly sequenced, and implementable before starting development.

**Workflow Position:** Runs AFTER `sdd:spec-generator` Phase 3 (tasks.md) and BEFORE `sdd:spec-qa-review` plan mode.

## Prerequisites

Verify these files exist in `project/work-items/{spec-name}/`:

1. `requirements.md` — user stories and acceptance criteria
2. `design.md` — architecture, components, data models
3. `tasks.md` — implementation tasks with requirement traces

## Review Process

### 1. Requirements Coverage

Extract every acceptance criterion from `requirements.md`. For each, verify at least one task in `tasks.md` has a matching `_Requirements: N.N_` trace. A single task may trace to multiple criteria via comma-separated values (e.g., `_Requirements: 1.1, 1.3_`).

**Flag as CRITICAL:** Any acceptance criterion with no corresponding task.

### 2. Design Coverage

Extract every component, interface, endpoint, and data model from `design.md`. For each, verify at least one task covers its implementation.

**Flag as CRITICAL:** Any design component with no corresponding task.

### 3. Sequencing

Verify task ordering respects dependencies:

- OpenAPI spec update before handler implementation
- Backend before frontend integration tasks
- Data model/schema tasks before service logic
- Unit tests within each task, integration/E2E tests at the end
- Checkpoint tasks every 3-5 implementation tasks

**Flag as MAJOR:** Dependency violations that would cause build failures.

### 4. Implementability

For each task, verify:

- **Clarity**: A developer could start without asking questions
- **File paths**: Reference real locations (verify they exist on disk) or clearly mark as new files to create
- **Scope**: Realistic for a single subagent (not too large, not trivially small)
- **No ambiguity**: No vague instructions like "add appropriate error handling"
- **Self-contained**: Task description includes enough context without reading other tasks

**Flag as MAJOR:** Ambiguous or unrealistically scoped tasks.

### 5. Completeness

Verify mandatory ending tasks exist:

- [ ] E2E test task (if applicable)
- [ ] Documentation update task
- [ ] Final validation task (full build + all tests)

**Flag as MAJOR:** Missing mandatory ending tasks.

## Severity Levels

- **CRITICAL**: Missing requirement coverage, missing design coverage
- **MAJOR**: Sequencing errors, ambiguous tasks, missing mandatory tasks
- **MINOR**: Scope suggestions, task splitting recommendations

## Output

Write `project/work-items/{spec-name}/task-review-summary.md`:

```
# Task Review Summary: {Spec Name}

**Review Date:** YYYY-MM-DD
**Status:** APPROVED | APPROVED WITH ISSUES | BLOCKED

**Statistics:**
- Requirements checked: N
- Tasks reviewed: N
- Critical: N | Major: N | Minor: N

## Coverage Matrix

| Requirement | Task(s) | Status |
|------------|---------|--------|
| AC 1.1     | Task 2  | ✅     |
| AC 1.2     | —       | ❌     |

## Issues Found

### CRITICAL-NNN: [Title]
**Issue:** [Description]
**Fix:** [Specific action]

### MAJOR-NNN: [Title]
**Issue:** [Description]
**Fix:** [Specific action]

## Verdict

[APPROVED/BLOCKED reasoning]
```

## Gate Behaviour

- **APPROVED** → delete `brainstorm.md` from the work-items directory, proceed to `sdd:spec-qa-review` plan mode
- **APPROVED WITH ISSUES** → warn user, allow proceeding if no critical issues
- **BLOCKED** → present issues, fix `tasks.md`, re-run this review. If blocked twice, ask the user.

## Next Step

On pass → invoke `sdd:spec-qa-review` in plan mode.
